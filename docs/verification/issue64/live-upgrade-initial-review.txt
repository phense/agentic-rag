## Findings

### H1 — Reader probes cannot authenticate on this host (rehearsal always fails)

- Where: `docs/verification/issue64/live-upgrade.py.txt:33` (`db.connect(cfg,role='reader')` in the old-code READ
  script) and `:133` (`db.connect(clone,role='reader')` for the new legacy read).
- Mechanism: `db.dsn(role='reader')` adds `user=rag_reader` (`agentic_rag/db.py:13-24`, same in 0.6.15). The driver
  runs as OS user `postgres` over the Unix socket. Live `pg_hba_file_rules`: the only `rag_reader` peer rules are
  database-specific (`agentic_rag`, `rag_dashboard_rehearsal_20261030`, …) with `map=rag-service`, whose ident map
  admits only system user `rag`; the generated clone `rag_bench_<hex>` falls through to `local all all peer` (no map),
  which requires OS user == DB user.
- Evidence: `sudo -u postgres psql -U rag_reader -d postgres -c 'select 1'` →
  `FATAL: Peer authentication failed for user "rag_reader"` (same rule path a `rag_bench_*` database takes).
  `old_read` therefore raises `CalledProcessError` at `:127`; L2 can never pass.
- Minimal fix (no pg_hba change): connect as the invoking DBA and drop privileges inside the session, identically for
  both sides so parity stays valid:
  - READ script: `with db.connect(cfg) as c: c.execute('SET ROLE rag_reader'); …search…`
  - new read (`:133`): `with db.connect(clone) as c: c.execute('SET ROLE rag_reader'); …`
  Neither 0.6.15 nor 0.6.17 search/indexes/retrieval/evidence/validity code issues `SET/RESET ROLE` or uses
  `session_user` on the read path (checked with `git grep` at both revisions); RLS then applies as `rag_reader`.

### H2 — Clone-name rewrite of the operator TOML is a no-op on the live files (rehearsal always fails)

- Where: `live-upgrade.py.txt:72-73`.
- Mechanism: `text.replace('name = "' + original_name + '"', …)` requires spaces around `=`. Both operator copies (and
  the live configs, byte-identical per `cmp`) use the shape `name="…"` (masked check: `xxxx="xxx…"`, exactly one
  `name` line, in `[db]`). Exact-match count for `name = "agentic_rag"` / `name = "rag_dashboard_rehearsal_20261030"`
  is 0 in all four files. The replace changes nothing and `assert load_config_text_name(text) == cfg.db_name`
  fails → rehearsal aborts. (Fail-safe: the assert prevents the old reader from ever pointing at the live DB.)
- Minimal fix: drop the textual rewrite; run the old process with `AGENTIC_RAG_CONFIG=<operator toml>` unchanged and
  pass the clone name as `argv[1]`, then in READ: `cfg=dataclasses.replace(load_config(), db_name=sys.argv[1])`
  (0.6.15 `Config` is a frozen dataclass at `config.py:44`, so `replace` is valid). Keep an assertion that the
  resulting `db_name` starts with `rag_bench_`. This also removes the reliance on the module global `original_name`.

### L1 — Post-traffic core check excludes too few operational tables (false block possible)

- Where: `live-upgrade.py.txt:25-26` used at `:156-157` (L9).
- `OPERATIONAL` omits tables the live API writes on legitimate client traffic: `service_windows`, `service_streams`
  (`service/ingest.py`), `service_session_access` (`service/session_logs.py`), `continuation_checkpoints`,
  `audit_log`, `mining_queue`, `embedding_reuse_cache`. Live `pg_stat_user_tables` shows all of these written on
  `agentic_rag`. Pure L8 reads do not touch them, so L9 passes if no other client writes between L7 and L9; any real
  ingest/save in that window yields `post_traffic_core_drift` and blocks the merge (fail-safe, no data risk).
- Minimal fix (optional, does not block): either state in PB L3/L8 that no other client writes until L9, or limit the
  L9 drift check to tables that must be immutable under reads and report the others as counts only. Non-blocking.
