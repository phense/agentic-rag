# Agent plugins, waiting requests and compaction

A central engine can serve many agent sessions without giving each session a
resident extraction process or database connection. Interactive tool calls use
two fixed foreground consumers. Original conversation evidence waits separately
for the single background source worker. Finishing compression does not require
finishing extraction.

Use [PB06801](playbooks/agent-plugins.md) to package, activate or update a client.
The [verification record](playbooks/evidence/agent-plugins.md) separates observed
behavior from native host UI and deployment scenarios still awaiting rehearsal.
Standalone remains the default; existing `rag install` adapters remain supported.

## Terms and access

A **source window** contains original redacted conversation evidence. Its
**receipt** confirms committed acceptance, not completed knowledge extraction.
A **foreground request** is a current tool invocation; its **request handle**
identifies queued/running/completed work. A **handoff** is an advisory continuation
checkpoint, not proof that newly extracted memories already exist.

The authenticated uploader owns request administration. Explicit teams share
history, subject to current project rights. Neither a Herdr session name nor a
prompt grants permission. IT and accounting credentials must have separate
allowed domains/projects/teams; an administrator can intentionally share selected
knowledge. Tokens stay in private files; packages contain paths, never token
values. The read-only package exposes read tools/status and installs no capture
hooks or cancellation tool. Department isolation also applies to result release.

Native plugin activation does not remove old raw hooks automatically. Disable
only the old owned integration when switching; running both can duplicate hook
work even though source/ACK replay remains idempotent. Subagent, fork, sidechain,
maintenance and recursive Stop payloads are suppressed by the native bridge.
`AGENTIC_RAG_HOOKS_DISABLE=1` disables lifecycle work without deleting buffers.

Gemini PreCompress is asynchronous/advisory and SessionEnd is best effort. It
cannot promise that a final shutdown callback will finish. Completed-turn and
BeforeModel captures preserve earlier original evidence; the next BeforeAgent
restores the retained advisory tail. The adapter handles bounded original
user/gemini JSON records and content patches in JSONL. Gemini records generated
compression summaries with the user role too. BeforeAgent can also contain a continuation generated by another hook; its
payload provides no reliable human-origin discriminator in the tested version.
Therefore both recording-user prose and observed BeforeAgent input remain
advisory assistant context, with original text/IDs/hashes retained separately.
Gemini capture cannot establish confirmed human authorization from these inputs.
Claude/Codex retain their existing original-source attribution. A future Gemini
origin discriminator requires a new source-backed regression before promotion. Original event IDs, timestamps
and hashes remain attached to normalized records. Keep the original host recording
when input is incomplete, changed unexpectedly or too large.

## Queued tool protocol

Legacy `/v1/tools/{name}` and remote MCP keep their synchronous protocol 1 shape.
The server advertises `extensions.queued_tools=1`; the new Python connector uses
that extension when advertised and falls back to synchronous tools on older
servers. The plugin-only MCP adds `memory_request_status` and, for a main
read/write client, `memory_request_cancel`.

`POST /v1/requests` accepts exactly these fields:

```json
{
  "idempotency_key": "a8ef54e0-5899-4eb8-ad14-81e66687e403",
  "created_at": "2026-10-30T01:00:00+00:00",
  "tool": "memory_domains",
  "arguments": {}
}
```

The initial timestamp must be within 60 seconds of server time. Persist the whole
envelope before networking. Replay it unchanged after an ambiguous ACK; changing
arguments gives 409 and renewing the timestamp risks creating different work.
An already retained identity is checked before the freshness rule. After bounded
cleanup, an old envelope is rejected, so it cannot repeat a canonical mutation.

A 202 response contains `durable=true`, `request_id`, `state`, `expires_at`,
`status_url` and `retry_after`. An opt-in `Prefer: wait=0.1` returns a completed
durable receipt inline with HTTP 200 when a consumer finishes within 100 ms. It
uses the same identity and atomic result as the queue; it never retries a write
through a second synchronous path.
Use `GET /v1/requests/{id}` to retrieve status/result and
`POST /v1/requests/{id}/cancel` to cancel. States are `pending`, `running`,
`completed`, `failed`, `cancelled`, `expired`. Knowledge effects and a completed
queued mutation's result commit together. Cancellation before that commit rolls
back effects; cancellation after completion reports completion and cannot undo
knowledge. Current credentials/session/scopes are rechecked before execution,
canonical commit and result release.

Concurrent result publication waits at most one second for its shared budget
lock. Longer contention rolls back uncommitted effects and returns the accepted
request to `pending` for a later attempt. The same handle remains valid; clients
must not submit a replacement mutation because publication is temporarily busy.

The connector persists input before capability discovery. Offline, busy or
expired-login discovery therefore returns a local handle. A legacy synchronous
server cannot deduplicate an ambiguous write: such a record is explicitly
`legacy_outcome_unknown`, retained for operator reconciliation, never replayed
automatically. Old unaccepted envelopes outside the 60-second window are blocked
for explicit reconciliation; the connector never silently retimestamps them.

A finite tool wait returns `waiting=true` and the handle. This is not a tool
answer. `durable=false` with `local.<uuid>` means the connector retained an
unconfirmed envelope; it must reconcile the same envelope before cancellation.
A network timeout never implicitly cancels accepted work. A source receipt or
queued extraction status must not be described as newly available knowledge.

## Finite resource defaults

| Resource | Bound |
|---|---:|
| Foreground consumers per API process |2 |

| Active foreground queue globally / per owner / per team |128 /48 /64 |
| Retained request rows including terminal records |4096 |
| New request envelope / stored result |60 KiB /120 KiB |
| Aggregate stored request arguments / results |4 MiB /8 MiB |
| Request execution/result lifetime from acceptance |300 seconds |
| Terminal tombstone cleanup |10minutes after expiry |
| Queue calls per authenticated uploader |12 per second;1024 bounded buckets |
| Client request outbox across all credential partitions |64 items /4 MiB |
| Existing source/checkpoint spool |2000 items /16 MiB, separate request budget |
| Background embedding page / call deadline |1 input /10 seconds |

The server also enforces the [database/free-storage/source-queue budgets](06-configuration-reference.md).
Finite backpressure remains necessary:429/507 before acceptance retains the
client envelope and requires retry with backoff. A full local spool refuses new
work while keeping existing pending input; retain the host transcript. Finite
results expire even if a client never retrieves them. Local pending request
records remain until reconciliation/consumption; UUID and local-ID retrieval
both consume terminal handles. Uploader observation rotates through all retained
records without consuming unread results; a partition for an old token
is not silently adopted by a replacement token.

Request waiting uses no per-session server process. Background extraction pauses
before a new job, curation/maintenance admission and each embedding page while
runnable foreground work exists. A mutation deferred specifically on source
backlog count/owner/byte pressure permits the bounded source worker to drain its
dependency; active retrieval still takes priority.
Embedding admission is shared in PostgreSQL, so lower Python priority alone is
not the mechanism. An already running background call cannot be preempted; its
page/deadline bounds the remaining contention. After current-work pressure
subsides, the single source worker resumes. Measured latency and background
throughput belong in the verification record, not a universal capacity promise.

`GET /v1/admin/status` exposes bounded aggregate foreground depth, oldest age,
input/result bytes and p95 wait/execution time alongside the existing source
queue. Bounded admission rejection counters are process-local and reset on API
restart; retained result-expiry counts and at most 64 team fairness summaries
come from the finite queue. This endpoint is the integration surface for future
request tracing (#60) and dashboard (#59), not a claim those UIs already exist.
It requires administrator authority and contains no prompts, result
contents, credential references or other users' individual request IDs.

## Client wait configuration

These optional `[service]` settings use seconds. They bound waiting, not the
server operation lifetime. Native hook process limits remain3 seconds.

```toml
[service]
tool_wait_seconds = 30 # range0.01..300
hook_wait_seconds = 1  # range0.01..5; keep below host hook process deadline
poll_seconds = 1       # range0.01..30; default jitter adds0..25 percent
```

Polling increases its interval up to 8 seconds with 0..25 percent jitter and
reserves a final 200 ms status lookup within the tool deadline. This final bounded
lookup may use a shorter interval when the hook deadline is about to end. The 12/s uploader allowance
still applies across concurrent sessions; waiting may return early under pressure.
After source ACK the private spool retains the latest 256 small receipt records,
not uploaded payloads. Resume reports up to 3 extraction states for that session
with bounded status lookup. Offline lookup labels the last observed state;
`queued` or `accepted` never means knowledge has applied.
